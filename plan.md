## 1. Product definition

AssestMe is a single-user web application for conducting structured IT assessments for small and medium-sized organizations.

The application must allow the administrator to:

1. manage clients and their sites;
2. optionally register generic or detailed IT assets;
3. maintain a reusable library of finding templates;
4. import and export finding templates in a versioned JSON format;
5. create an assessment for a client;
6. add, edit, duplicate, order, and remove findings from a spreadsheet-like grid;
7. associate a finding with the whole organization, one or more selected sites, a network scope, selected assets, or a custom scope;
8. define multiple remediation solutions for the same finding;
9. select one recommended solution and, when the finding is resolved, one implemented solution;
10. evaluate the priority of intervention manually or through a configurable consequence × likelihood matrix;
11. express the implementation effort and an indicative economic estimate without creating a quotation;
12. attach images, PDFs, documents, logs, links, and other evidence;
13. generate a professional configurable PDF report;
14. generate an XLSX export containing the complete textual summary of the assessment;
15. archive or permanently delete data according to the configured deletion policy.

The application is not:

- a quotation or invoicing system;
- a project management system;
- a vulnerability scanner;
- a CMDB requiring complete asset registration;
- a multi-tenant SaaS;
- a client portal;
- an AI service;
- an audit-trail system;
- a document version-control system.

AI is external to the application. It may generate JSON template libraries, but AssestMe does not record or infer whether a template was generated by AI.

### D-001 — Framework

Use Laravel 13 and Filament 5 Panel Builder with Livewire 4.

### D-002 — Product boundary and account model

AssestMe is an internal, single-instance, multi-client application used by one administrator.

Requirements:

- exactly one row may exist in `users`;
- no public registration;
- no client authentication;
- no role/permission package;
- no audit log;
- no change-history/version browser for findings;
- no public API or MCP server in v1;
- no portal, quotation, ticketing, scanner, Jira, or runZero integration in v1.

Enforce the single-user rule with a unique `singleton_key` column fixed to `1`, application validation, and tests.

### D-003 — Linux baseline

Development and production documentation target Ubuntu Server 24.04 LTS.

Supported CPU architectures are `amd64` and `arm64`. CI runs on `amd64`. Stop before executing OS package commands on a different distribution.

### D-005 — Database

Use one SQLite file:

```text
database/database.sqlite
```

Connection settings:

```text
foreign_keys = ON
journal_mode = WAL
busy_timeout = 5000 ms
synchronous = NORMAL
transaction_mode = IMMEDIATE
```

Rules:

- do not use SQLite-only schema types or raw vendor-specific migration syntax;
- use portable Laravel migrations;
- verify the effective PRAGMAs at application startup in local/testing and through `assestme:diagnose`;
- use `IMMEDIATE` transaction mode for write transactions so lock acquisition fails before partial workspace processing;
- treat `database is locked` as a visible failure;
- do not retry indefinitely.

### D-006 — Queue, cache, and sessions

Initial runtime:

```dotenv
QUEUE_CONNECTION=sync
CACHE_STORE=file
SESSION_DRIVER=file
```

No Redis, Horizon, queue worker, or asynchronous report generation.

### D-007 — Frontend build

Application runtime and normal development must not require Node.js or a frontend build.

Allowed:

- Filament's published compiled assets;
- Blade;
- Livewire;
- Alpine bundled by Filament;
- plain application-owned JavaScript registered through Filament asset management;
- Composer packages.

Dusk may install Chrome/ChromeDriver only in development and CI. It is not a production dependency and is not a build step.

### D-008 — Central assessment grid

Use only native Filament 5 form and schema components for the first implementation of the assessment workspace.

The central findings grid uses a native Filament `Repeater` configured with its table layout through `Repeater::table()`. Each finding remains a related Eloquent record managed through the Repeater relationship.

Use native Filament components inside the table:

- `Textarea` for the multiline problem, recommended-solution summary projection, and entrepreneur-facing notes;
- `TextInput` for short text and monetary values;
- `Select` for category, priority, effort, estimate type, and status;
- `Toggle` or `Checkbox` for report inclusion;
- native Repeater item actions for creation, cloning, deletion, and reordering.

Do not install a third-party grid, table-repeater, or spreadsheet package for the assessment workspace in this phase. Do not create a custom JavaScript spreadsheet component in this phase. The native implementation is the primary implementation, not a fallback.

The first release does not require:

- multi-cell copy and paste;
- range selection;
- Excel-style fill handles;
- column resizing;
- arbitrary column reordering;
- table pagination inside the assessment form.

These capabilities may be reconsidered only after the native workspace has been implemented and tested with real assessments.

Milestone 0 must prove that the native Repeater table can:

- render multiline `Textarea` fields and preserve line breaks;
- persist a `HasMany` relationship;
- add, clone, delete, and reorder findings;
- manage at least 10, 25, and 50 findings;
- use controlled autosave and explicit save through the same application service;
- display validation and persistence errors without losing current form state.

If a native capability does not behave as required, record the exact limitation in Discoveries. Do not install an alternative plugin without explicit approval.

### D-010 — Report model

Provide one Blade report layout with configurable sections and branding.

Users cannot upload or edit Blade templates.

### D-011 — Language

The v1 UI and report are Italian.

Code, identifiers, tests, comments, and commits are English.

All user-visible application strings use Laravel translation keys. Template records do not contain a locale field; their language is their content language.

### D-012 — Template contract

JSON Schema Draft 2020-12, `schema_version = 1`, is canonical.

Use `opis/json-schema` directly. Application validation adds cross-record checks that standard JSON Schema cannot express.

CSV/XLSX template import is outside v1. JSON export is required.

### D-013 — Priority

Default mode:

```text
matrix_with_override
```

Manual override is available only on editable assessments and always requires a reason.

### D-014 — Estimates

Supported estimate types:

- `exact`;
- `range`;
- `bundled`;
- `requires_quote`;
- `requires_analysis`;
- `variable`;
- `not_applicable`.

No total is calculated or displayed.

### D-015 — Scope and assets

Finding scope values:

- `organization`;
- `selected_sites`;
- `network`;
- `selected_assets`;
- `custom`.

Asset records are optional.

### D-016 — Saving

Provide:

- autosave for committed field changes;
- explicit **Salva assessment** for full draft validation and persistence;
- separate **Completa assessment** for completion validation and state transition.

Autosave never marks an assessment completed.

### D-017 — Deletion

Global setting:

- `archive`;
- `permanent`.

Permanent deletion uses staged file moves and recovery records as defined later.

### D-018 — Failure behavior

No silent degradation.

A failure must:

1. leave persistent data in a known state;
2. log structured context;
3. show an actionable Italian error;
4. avoid success notifications;
5. be covered by a failure-path test where practical.

### D-019 — Deployment

Local development:

```text
http://127.0.0.1:8000/admin
```

Production:

- Nginx;
- PHP 8.3 FPM;
- application releases under `/var/www/assestme/releases`;
- `/var/www/assestme/current` symlink;
- shared data under `/var/www/assestme/shared`;
- TLS through Certbot when a valid FQDN is supplied.

A production deployment requires the operator to provide `ASSESTME_HOSTNAME`. The development milestone does not depend on a public hostname.

### D-020 — Concurrency

Every assessment has `lock_version`.

Every save request has a UUID idempotency key and expected version. A stale version causes a conflict; the server never performs last-write-wins.

### D-021 — Lifecycle

Assessment status:

- `draft`;
- `completed`;
- `archived`.

Completed and archived assessments are read-only. Reopening is explicit.

### D-022 — Report immutability

Each generated PDF/XLSX stores:

- complete normalized data snapshot;
- settings snapshot;
- payload SHA-256;
- file SHA-256;
- sequential version number.

The stored file is authoritative. Re-rendering a snapshot may be data-equivalent but is not promised to be byte-identical.

### D-023 — File deletion

Files are atomically renamed within the same filesystem into a private trash operation directory before database deletion. Database failure restores them. Post-commit physical cleanup is tracked and retryable.

### D-024 — Finding solutions

All finding solutions use soft deletes.

A solution selected as recommended or implemented cannot be deleted. The administrator must reassign or clear the reference first.

### D-025 — Import update semantics

Template and solution `external_id` fields are stable lowercase identifiers.

Updating an existing template is a complete replacement of all import-managed fields and solutions inside one transaction.

### D-026 — XLSX

Use `phpoffice/phpspreadsheet` directly. Do not rely on a transitive dependency of a Filament export plugin.

### D-027 — Browser testing

Use Laravel Dusk with Chrome/ChromeDriver in development/CI. No Node.js or Playwright.

The maintained Dusk suite is the automated browser gate while the application is under active development. It covers the browser behaviors already represented by executable tests and must run against an isolated disposable database and storage root.

Manual Edge, Firefox, iOS Safari, Android Chrome, camera, and device-specific checks are deferred until a reference installation and suitable devices exist. They are compatibility evidence for a later production-release decision and do not block development milestones.

### D-041 — Autonomous isolated verification

No development or CI verification command may read, migrate, truncate, seed, back up, restore, benchmark, or otherwise mutate the configured application database or private storage.

Required behavior:

- the maintained entry points `php artisan test`, `composer quality` (including Canary), `composer browser` (Dusk), the benchmark, and `scripts/verify.sh` use disposable file-backed SQLite databases created specifically for that run;
- test cache, sessions, generated reports, evidence, backups, temporary uploads, and deletion trash use disposable test roots;
- verification creates its own domain fixtures and administrator when required;
- commands clean their disposable state on success and failure;
- a missing seed, template, administrator, or reference assessment in the application database cannot make a test or benchmark fail;
- the application may have no initialized reference database while development is in progress;
- `scripts/bootstrap-local.sh` is an explicit installation command and is the only development helper allowed to initialize the configured local application database;
- tests proving backup/restore or deployment behavior operate only on temporary paths.

Until a reference installation and test devices exist, the blocking automated gate is Composer validation/audit, Pint, PHPStan, Pest, Canary strict zero-skip, the maintained Dusk suite where ChromeDriver is available, diagnostics against an isolated initialized database, the isolated 50-finding benchmark, storage audit, and `scripts/verify.sh`. Manual cross-browser/device QA is recorded as deferred, never falsely reported as passed.

### D-028 — Authentication and MFA

TOTP MFA is optional and disabled until the administrator enables it.

When enabled:

- generate eight single-use recovery codes;
- require the user to confirm storage of the codes;
- provide `php artisan assestme:reset-mfa`;
- do not use email recovery.

### D-029 — Backups

Implement application-aware local backups with a restore test. Off-host copying and encrypted storage are operational responsibilities outside v1.

### D-030 — Dependency locking

`composer.lock` must be committed.

The plan specifies package constraints; the exact versions resolved in Milestone 0 become immutable until a reviewed dependency-update change.

### D-031 — Community packages

Inspect licenses, Composer metadata, source, tests, and advisories before acceptance.

Do not edit `vendor/`. Do not fork without explicit approval.

### D-032 — Time

Store timestamps in UTC. Render them in `Europe/Rome`.

`assessment_date` is a date-only value and is not converted across time zones.

### D-033 — Identifiers

Use auto-incrementing integer primary keys.

Use UUID strings only for:

- idempotency request keys;
- deletion operation IDs;
- generated correlation IDs.

### D-034 — Historical data

No audit log or editable history is required.

Generated report snapshots provide immutable delivery history.

### D-035 — Future integrations

Keep business logic in application actions/services so future integrations can call it, but do not create speculative API contracts or adapters in v1.

### D-036 — Univer Sheet

Do not install `yuichi-okada/filament-univer`. Its single JSON spreadsheet document is incompatible with the relational finding/solution/asset/evidence model and would create a second source of truth.

### D-037 — Auxiliary table plugins

Install Right Click and Advanced Table Export only after standard Filament resources exist.

- Right Click duplicates visible accessible actions on standard resource tables; it is never the only interaction path and is not integrated into the assessment workspace.
- Advanced Table Export serves generic client/template/asset/assessment lists. It does not generate the assessment workbook, which uses the dedicated PhpSpreadsheet exporter.

- if a user exists, exit non-zero unless `--replace` is supplied;
- `--replace` requires current password or interactive confirmation from the console;
- enforce password policy;
- never create a second user;
- never print a production password;
- local bootstrap may generate and print a random password once;
- the command is intentionally not idempotent: without `--replace`, an existing administrator is an explicit non-zero error.

`migrate:fresh --seed` seeds domain data only. It never creates an administrator.

Tests create their administrator through factories.

### 5.11 Deployment and rollback

`deploy-production.sh` must:

1. verify clean release source and `composer.lock`;
2. create a timestamped release;
3. run `composer install --no-dev --classmap-authoritative`;
4. link shared `.env`, database, and storage;
5. enable maintenance mode;
6. create a pre-migration backup;
7. run `php artisan migrate --force --isolated`;
8. run `php artisan filament:assets`;
9. run `php artisan optimize`;
10. run diagnostics and smoke tests;
11. switch the `current` symlink atomically;
12. reload PHP-FPM;
13. disable maintenance mode.

Failure before symlink switch removes the failed release and restores the pre-migration database if it was changed.

A rollback switches to the previous code release and restores its matching database/storage backup. The command must warn that restoring a database discards writes made after the backup.

### 5.12 Backups

Implement:

```text
php artisan assestme:backup [--output=/absolute/archive.tar.gz]
php artisan assestme:backup:verify <archive>
php artisan assestme:restore-backup <archive>
```

Backup content:

- consistent SQLite backup created using SQLite's backup/VACUUM mechanism after WAL checkpoint;
- private storage;
- generated reports;
- settings and application version metadata;
- manifest with SHA-256 per file.

Schedule daily at 02:30 Europe/Rome through Laravel Scheduler and one system cron entry.

Retention:

- 7 daily;
- 4 weekly;
- 6 monthly.

Backups are stored under `/var/backups/assestme` with mode `600`.

Off-host copying and encrypted-volume protection are required operational controls but are outside application code.

Restore:

- requires maintenance mode;
- verifies manifest hashes;
- creates a safety backup before replacement;
- restores database and storage together;
- runs diagnostics;
- exits non-zero on any mismatch.

Run an automated restore test against temporary paths in CI and a manual production restore test at least quarterly.

## 10. Assessment persistence, autosave, and conflict protocol

### 10.1 Persistence units

- the native Repeater may submit the complete relationship workspace for both controlled autosave and explicit save;
- new Repeater items carry a stable temporary UUID until persistence and receive a server mapping to their database ID;
- adding a blank finding through the definitive application service persists it immediately;
- copying a template persists finding and solutions immediately;
- adding a solution/evidence persists it immediately after valid required input;
- field autosave may send one assessment-metadata/finding patch or the complete workspace state;
- explicit save sends the complete workspace.

No unsaved database row relies on a temporary primary key.

### 10.2 Request contract

Every save request includes:

```json
{
  "request_id": "UUID",
  "assessment_id": 123,
  "expected_version": 7,
  "tab_id": "UUID",
  "scope": "workspace",
  "record_id": null,
  "payload": {},
  "payload_sha256": "..."
}
```

### 10.3 Server algorithm

1. Validate request UUID and payload hash.
2. Return stored response if `request_id` was already applied.
3. Acquire `assessment:{id}:save` lock for 10 seconds, wait max 5 seconds.
4. Start transaction.
5. Update assessment using `WHERE id = ? AND lock_version = expected_version`.
6. If zero rows update, throw `AssessmentVersionConflict`.
7. Validate and persist the patch or complete Repeater workspace, mapping stable temporary UUIDs to persisted integer IDs.
8. Increment `lock_version`.
9. Store idempotency result.
10. Commit and release lock.
11. Return the applied version, normalized saved values, and temporary-UUID-to-ID mapping.

### 10.4 Client scheduling

Only one save request may be in flight per workspace tab.

- multiline fields: save on blur;
- short text fields: trailing 500 ms;
- select/toggle: trailing 250 ms;
- multiple changes in the same finding while a request is in flight are coalesced into the next patch;
- no per-keystroke request for multiline fields.

The client ignores an obsolete response when a newer local state or request sequence already exists. Autosave and the explicit-save button invoke the same application service.

Transport failure:

- retry once after 1 second with the same request UUID;
- no automatic retry for validation, conflict, lock timeout, or server error.

### 10.5 Conflicts and multiple tabs

Multiple tabs are allowed but not merged.

A stale tab receives conflict status and becomes read-only until the user reloads. The server value wins only after explicit reload; local unsaved state is not silently discarded.

### 10.6 Offline/close behavior

When offline:

- show Offline;
- stop sending;
- retain current browser state;
- show `beforeunload` warning for unsaved changes;
- do not claim offline persistence.

Reconnect triggers explicit retry/save by the user.

### 10.7 Buttons

**Salva assessment**:

- draft validation;
- complete workspace persistence;
- does not complete.

**Completa assessment**:

- completion validation;
- transition to completed;
- read-only.

**Riapri assessment**:

- confirmation;
- completed to draft;
- increments version.

### 10.8 Validation

Autosave permits incomplete draft rows but validates type/length/ownership/security constraints.

Completion/report validation applies only to included findings and returns row-numbered errors.

### 10.9 Error preservation

Validation/database errors leave Livewire form state intact. The error remains visible until successful save or explicit dismissal. The last successful version remains unchanged.

Matching is case-insensitive Unicode-normalized by name.

Unknown category/tag:

- create automatically during the import transaction;
- generate slug with Laravel slugification;
- resolve collision with numeric suffix;
- never rename an existing category/tag based on import text.

### 11.4 Preview

Preview shows:

- create;
- replace;
- unchanged;
- invalid;
- field-level differences for replaced templates.

User chooses one global conflict mode:

- replace existing;
- skip existing;
- cancel.

No per-row deselection in v1.

### 11.5 Replace algorithm

Matching template: exact normalized `external_id`.

Replace mode:

1. update all template import-managed fields;
2. sync category/tags;
3. match solutions by solution `external_id`;
4. update matched solutions;
5. create new solutions;
6. soft-delete template solutions absent from the file; detached assessment findings are unaffected;
7. set the one recommended solution;
8. leave unrelated category/tag records untouched.

Fields are full-state: explicit `null` clears a nullable field. Omitted required fields invalidate the file.

`active=false` disables the template only.

Renaming an external ID creates a new template. The old template is not inferred or deleted.

### 11.6 Transactionality

The selected operations for the entire file execute in one transaction. Any error produces zero changes.

### 11.7 Schema versions

Only version 1 is accepted.

A future version requires:

- separate schema file;
- explicit migrator;
- tests;
- signed decision update.

### 11.8 Export

Deterministic JSON:

- UTF-8;
- pretty-printed;
- fixed key order;
- templates sorted by external ID;
- solutions sorted by sort order then external ID;
- tags sorted by normalized name;
- no database IDs/timestamps.

Default export includes active templates. UI can explicitly include inactive templates.

Round-trip tests must prove no data loss.
